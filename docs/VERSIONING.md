# 版本与兼容策略

## 五类版本

1. **应用版本**：使用 `MAJOR.MINOR.PATCH`。破坏兼容的交互或数据变更提高主版本；新增兼容功能提高次版本；修复提高补丁版本。
2. **用户数据 schema**：`meal_user_states.schemaVersion` 独立递增。每次升级必须提供从旧版本向前迁移的测试样本。
3. **AI 计划契约**：生成请求和响应包含 `contractVersion`。云函数只接受已知版本，并对全部字段、数量、长度和枚举值重新校验。
4. **计划内容版本**：每份已确认计划保存自己的 `planVersion`、生成时间与生成依据摘要。应用升级不覆盖用户计划。
5. **AI 生成器版本**：每个生成任务保存 `plannerVersion`，用于区分提示词、分片和校验策略。只改变生成器但不改变请求/响应结构时不提高 `contractVersion`；已经确认的计划不因生成器升级而重写。

当前未发布版本使用 AI 生成器 `4`：提纲只保存全局标题和依据，详情按最多 4 个餐位分片生成主题、餐名与食材。详情分片按索引顺序领取，后续分片从已完成结果稳定派生餐名禁用清单；重复餐名会在当前分片重试，最终计划仍执行严格全局去重。外部计划契约仍为 `contractVersion: 1`，用户数据为 schema v6；已经确认的计划保持不变。schema v6 增量迁移 v1-v5，并把采购勾选与晚餐选择按计划 ID 保存，历史达到 64 份时显式拒绝继续替换而不淘汰旧记录。版本 3 进行中任务不会由版本 4 静默接管，而是明确终止并由用户重新发起。

仓库根目录的 `release-manifest.json` 是机器可检查的版本清单，其中 `aiPlannerVersion` 必须与云函数导出的 `PLANNER_VERSION` 一致。开发中的版本使用 SemVer 预发布标识（例如 `0.2.0-dev.0`）；正式发布时同步更新最后发布版本、工作版本和发布状态，不能只修改展示文字。

## Branches 与 Tags

- **Branch** 是仍会增加提交的当前版本工作线。按项目约定只长期保留一个版本 Branch，名称为目标正式版本；当前是 `refs/heads/v0.2.0`。开发期间 `release-manifest.json` 仍使用 `0.2.0-dev.1`，不能因为模块提交而逐次升版。
- **Tag** 是正式版本的不可移动快照，统一使用带 `v` 的版本号；历史基线是 `refs/tags/v0.1.0`，本轮正式发布点将是 `refs/tags/v0.2.0`。Tag 推送后不得移动、覆盖或复用。
- `main` 只用于首次迁移或 GitHub 默认分支切换的短暂过渡，不与当前版本 Branch 长期并行维护。
- Branch 与 Tag 可能在切换下一版本前短期同名。脚本、文档和人工命令必须使用 `refs/heads/...` 或 `refs/tags/...` 全名，GitHub 上分别从 **Branches** 和 **Tags** 页面查看，禁止依赖有歧义的短名称。
- GitHub Actions 同时监听过渡 `main` 与 `v*` 版本 Branch。安全工作流使用完整历史，既检查最终树，也阻止把敏感内容先提交、后删除再整体推送。

版本轮换顺序固定如下：

1. 在唯一当前 Branch 上按模块提交，所有未发布提交继续记录到 `CHANGELOG.md` 的 `Unreleased` 和 `docs/ITERATION_LOG.md`。
2. 完成自动测试、开发者工具、云端闭环、跨设备恢复、第二账号隔离、隐私及敏感信息检查后，创建唯一的正式版本提交。
3. 正式版本提交一次性归档 `CHANGELOG.md`、同步 `release-manifest.json` 和 README，再创建同版本 annotated Tag。
4. 开始下一版本时，从上一正式 Tag 创建新的唯一版本 Branch，切换 GitHub 默认分支并删除上一版本 Branch；上一版本只由 Tag 永久保留。

`v0.1.0` 是针对 `2026-08-25` 首个原生小程序基线追溯建立的源码 Tag。它用于准确定位旧源码，不表示当时已经完成 GitHub Release 或微信正式发布流程。

## 迭代状态与支持

- `CHANGELOG.md` 的 `Unreleased` 只表示正在开发或等待验证，不能对外宣称已经发布。
- 每次正式发布把已完成条目归档到带日期的版本，更新 `release-manifest.json`，创建同版本 Git tag，并保留对应迁移测试。
- GitHub Issue 只接收脱敏后的可复现问题和功能建议；当前维护范围、所需信息和私密安全报告路径见 `SUPPORT.md` 与 `SECURITY.md`。
- 研究结论必须写明搜索范围、许可证、维护状态和适配差距。“尚未发现满足完整闭环的单一项目”不等于“GitHub 缺少相关项目”。

## 每次迭代说明

每个 Pull Request 和正式版本说明必须按以下顺序写清楚，不能只写“优化”或“修复若干问题”：

1. **用户变化**：用户先做什么、页面或结果发生什么变化，包含加载、空状态、失败和恢复路径。
2. **调研与复用**：搜索过的现有项目、许可证、固定 commit（如有引入）、可复用部分和最终取舍。
3. **兼容矩阵**：应用版本、`schemaVersion`、`contractVersion`、`plannerVersion`，以及最低微信基础库和云函数运行时要求。
4. **数据影响**：新增或修改哪些集合与字段，从哪些旧版本迁移，迁移是否幂等，哪些用户数据保持不变。
5. **隐私影响**：是否新增健康、位置、图片或第三方服务数据；发送范围、保留期限和删除路径是什么。
6. **部署顺序**：先部署哪些云函数、再上传哪个小程序版本，部署者本人需要填写哪些占位配置。
7. **验证证据**：自动测试、开发者工具编译、真机、多设备恢复、第二账号隔离和敏感信息检查的结果。
8. **回滚条件**：哪些部分可以回滚、最低兼容 schema 是多少、回滚后是否仍可读取新版本写入的数据。
9. **已知限制与支持**：未完成能力、服务商限制和对应 Issue；公开反馈不得包含密钥或个人数据。

`CHANGELOG.md` 记录面向使用者的结果，Pull Request 记录上述完整证据，`release-manifest.json` 保存机器需要检查的当前版本。使用问题按 `SUPPORT.md` 分流，安全问题按 `SECURITY.md` 私下报告。

## 升级不丢数据

- 云数据库是数据真源，本地缓存只作离线快照。
- 迁移采用增量写入；未知的未来字段不得因旧客户端保存而被删除。
- 发布新 AI 提示词或模型不会自动重生成计划。用户必须主动发起、预览并确认。
- 新计划确认前保留上一份已确认计划；生成失败不回退到内置食谱。
- 采购勾选按稳定条目 ID 保存。更换计划时只保留新清单中仍存在的 ID。
- 旧版静态计划只作为历史 schema 迁移输入，不作为新用户默认计划。
- 旧客户端或旧云函数遇到高于自身支持范围的未来 schema 时必须拒绝读写并提示升级，禁止把未来 schema 降级写回。
- 用户生成下一期 14 天时创建新的计划 ID 和内容版本；生成过程只写临时任务与候选计划，确认事务成功后才替换当前计划，上一份计划进入历史。用户档案、健康记录、运动记录和私人照片不属于计划对象，不随计划替换；采购勾选只保留新旧清单中稳定 ID 相同的项目。

## 回滚边界

- 小程序界面可以回滚到仍支持当前 `schemaVersion` 和 `contractVersion` 的版本；不满足支持范围时必须停止写入并提示升级。
- 云函数不得回滚到会把当前 schema 降级写回的版本。数据库结构或迁移上线前先做云端备份，回滚代码不等于回滚用户数据。
- AI 生成器回滚只影响之后新发起的任务，不修改已经确认的计划。进行中的任务继续由创建它的 `plannerVersion` 标识，不能用另一版本静默接管。
- 发布失败时保留现有 `activePlan` 和用户状态，先撤回有问题的客户端或云函数；不得通过清空集合恢复服务。

## 发布流程

1. 将变更写入 `CHANGELOG.md` 的 `Unreleased`。
2. 在当前版本 Branch 上按模块提交；只有版本维度确实变化时才更新应用、schema、AI 契约或生成器版本，并补充对应测试。
3. 运行本地验证、微信开发者工具编译/预览、云函数测试、隐私与敏感信息扫描。
4. 在同一微信号跨设备验证恢复，再用第二微信号验证隔离。
5. 到达发布冻结点后，把 `Unreleased` 归档到正式版本和日期，原子同步版本清单、README 与上传描述并创建发布提交。
6. 创建指向该发布提交的本地 annotated Tag，上传完全相同的提交作为微信开发版本并完成最终真机回归。
7. 最终回归通过后推送当前 Branch 和 Tag，再提交微信审核与发布。已经推送的 Tag 永不移动；若发布后发现问题，使用新的补丁版本修复。

逐项操作和证据要求见 `docs/RELEASE_CHECKLIST.md`。
