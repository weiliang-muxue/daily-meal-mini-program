# 0.3.0 功能完善与验收清单

更新日期：2026-10-09。开发 Branch 为 `refs/heads/v0.3.0`，应用 `0.3.0-dev.0`，未发布；线上仍为 `0.2.1`。本文件不含真实用户记录、服务配置或凭据。

## P1：个人食材与采购联动

本地代码及离线回归已完成，尚未部署或完成手机验收。

- 在“调整这一餐”中修改、增加或移除食材，填写数量、单位和采购分类；每餐 1–30 项，数量为 0.001–100000，最多三位小数。
- 先预览采购变化，再明确确认保存；预览不会写入，取消预览不改变当前餐单。预览期间餐单、采购状态或身份变化时要求重新核对。
- 同分类、同单位、规范化后同名的食材合计；不同单位不猜测换算。仅统计选中的晚餐，不把运动/不运动两个备选同时计入。
- 实际数量变化的采购项需要重新勾选；未变化项保留。只改餐名/做法或未选中的备选餐，不取消当前采购勾选。
- 个人调整保存在原有 `mealOverrides`，不改写基础餐单、其他餐食或历史；恢复原餐使用相同采购重算逻辑。
- 旧的文字食材说明保留，不猜测其中的份量。完整结构化餐单可以把用量明确改成新方案；没有完整食材结构的旧餐单仍只编辑文字，并明确提示不自动更新采购。
- 输入非法时拒绝本次修改，不能退回默认状态而丢掉已有餐单。断网时保留当前身份的待同步修改，明确提示尚未云端保存；后续重试继续同步。

### 数据兼容与部署顺序

用户 schema 从 v8 增量到 v9，新增 `mealOverrides[mealId].ingredientItems` 可选数组。v8 的喝水设置、提醒版本、餐单与采购等均保持；v1–v7 继续原有迁移。不会重建集合、清空文档或批量补写个人记录。

共享采购逻辑同时进入小程序、`userData`、`aiPlanner`。`userData` 事务内重新验证食材和受影响勾选，不信任客户端计算；保存要求 `clientSchemaVersion: 9`。旧客户端保存会得到升级提示，不能覆盖新字段。

不能单独把 schema v9 的 `userData` 部署到仍供旧客户端使用的正式环境，也不能让旧 `aiPlanner` 写回 v9 文档。先在测试环境使用同一冻结源码部署兼容 v9 的 `aiPlanner` 和 `userData`，验证新版小程序，再安排正式切换窗口与客户端升级；旧 worker 必须已退出或结束，不能新旧写入器并行。此轮没有进行任何云端迁移、部署或上传，不将 Git 提交等同于发布。

### 已完成的测试证据

- `node scripts/validate.js`：61 组项目回归，涵盖共享状态、云函数事务、离线待同步、身份隔离、页面模拟、静态适配及安全规则。
- 新增虚构的 1/7/14 天多餐采购测试：增/删/改食材、重复食材合计、单位隔离、所选晚餐、无关勾选保留、恢复原餐及历史、v8→v9 幂等迁移。
- 新增页面模拟：预览不写入、取消预览、状态冲突阻止确认、明确确认保存、身份切换中断，以及首次身份绑定。
- 新增保存保护：云端拒绝非法数量/旧 schema 写入、服务器独立清除受影响勾选；客户端断网后重启并继续同步结构化个人修改。
- UI/UX 规范用于保留现有原生视觉样式、可访问标签、至少 48px 触控区域和页面内错误提示。静态宽度检查、模拟页面不等于微信原生渲染或 Android/iOS 真机验收。

## P4：收藏、偏好与忌口（待开发）

收藏用于再次安排，不喜欢用于软偏好，过敏/忌口作为明确限制，三类分别保存、可修改，不能互相推导。再次安排先预览日期、餐次与采购变化。数据集搜索仅在固定 commit、许可证和来源审计完成后另行接入；不抓取在线服务替代授权，不把未验证的 AI 输出描述为无过敏风险。
