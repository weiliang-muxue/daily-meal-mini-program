# 第三方菜谱数据评估与接入边界

核验日期：2026-09-02

本文记录第三方菜谱数据的评估结论和未来接入门禁，不代表当前版本已经引入相关内容，也不替代发布主体结合实际用途进行的法律审查。

## 1. 当前结论

- `v0.2.0` **不导入、复制、改写、打包或运行任何第三方菜谱数据、图片、代码或服务**。
- 当前发布候选不得新增第三方菜谱依赖、远程地址、缓存副本或构建产物。
- 若后续需要菜谱参考，固定提交中的结构化 JSON 已完成许可证核验，可按本文边界接入；本项目不需要 `vibe-cook-backend` 的应用代码。
- 是否接入数据必须作为后续独立版本决策，完成本文全部门禁后再实施，不能混入 `v0.2.0` 发布修复。

这意味着“只要数据集”在技术上足够：应用继续使用本项目自己的微信原生页面、云函数、AI 餐单契约、用户隔离和迁移逻辑；第三方 JSON 最多作为离线、只读的菜谱知识来源，不能替代本项目业务代码。

## 3. 允许与禁止的范围

### 3.1 未来可接入的唯一数据范围

未来版本只能从 `dataset@b227b896d650709aa345e639634ecd5c3358e607` 离线取得以下文件：

- 索引：`json/index.json`；
- 菜谱详情二选一：
  - 单文件形态：`json/recipes.json`；或
  - 分文件形态：`json/recipes/*.json`。

一次导入必须只选择一种详情形态作为权威输入，不能同时合并 `json/recipes.json` 与 `json/recipes/*.json`，以免重复、覆盖顺序不确定或两种表示发生漂移。`json/index.json` 只承担索引和来源路径映射，不得在详情冲突时静默覆盖权威输入。

数据必须在受控的离线导入流程中完成校验、筛选和本地索引生成。小程序运行时不得依赖上游仓库可用性。

### 3.2 明确禁止

以下内容在当前版本和本文定义的 JSON 接入方案中禁止：

- `vibe-cook-backend` 的 `main` 分支应用代码、构建产物、依赖、数据库实现或配置；
- 任何受 Business Source License 1.1（BUSL 1.1）约束的应用代码，无论是复制、改写、编译、链接还是作为发布依赖；
- `cook.corerevive.cn` 或其他上游在线 API、网页抓取、运行时代理和服务端热链；
- GitHub Raw、Git LFS、上游 CDN 或其他第三方地址的运行时热链；
- `images/ai-generated/`、`images/overview/`、`images/steps/` 及数据集中所有其他图片；图片接入暂缓，只有未来另立范围并完成逐项权利核验后才能重新决策；
- JSON 中的图片路径、图片 URL 或可被客户端拼接成远程图片地址的字段；
- `vibe_cook.db`、未列入允许范围的清单文件或其他仓库文件；
- 无法建立来源记录、许可证范围不清楚或内容权利状态无法确认的条目。

图片即使与 JSON 位于同一数据分支，也不进入当前 JSON 接入方案。The Unlicense 文件不能替代对图片生成来源、训练素材、人物肖像、商标、包装和第三方作品权利的逐项核验；在该核验完成前，全部图片保持暂缓和禁入状态。

## 4. 许可证判断边界

The Unlicense 提供复制、修改、发布、分发和商业使用许可，不强制署名或保留 NOTICE，并包含“按原样提供”和不担保条款。`dataset@b227b896d650709aa345e639634ecd5c3358e607` 中本文列出的 JSON 已按该提交的根 `LICENSE` 和 README 完成许可核验，可以进入后续技术与内容接入流程，无需等待额外的 JSON 许可证批准。

为便于版本复现、问题撤回和上游更新审计，本项目自愿保留来源、固定提交、许可证文本和修改记录。这是项目治理选择，不是将许可范围缩小，也不是声称 The Unlicense 要求署名。

许可证核验不等于对内容作出以下保证：

- 菜谱事实、营养值、过敏原和健康建议准确；
- 菜名、品牌名、人物、商标或其他第三方权利已清除；
- 数据中的每个字段都由仓库维护者原创；
- 上游历史版本与当前核验快照具有相同许可证；
- 数据适合直接作为医疗、营养治疗或个体化健康建议。

因此，导入后的菜谱仍须经过内容、安全和产品审核；不得把开源许可证当作健康建议免责或内容正确性证明。

## 6. 分阶段接入门禁

固定提交 JSON 的许可证结论已经明确，不需要在接入时再次等待许可批准。只有以下技术、内容、完整性和发布治理步骤全部通过，后续版本才能包含第三方 JSON：

1. **版本隔离**：从 `v0.2.0` 之后的新功能分支开始，先写独立需求、风险和回滚方案。
2. **提交冻结**：导入器只允许访问固定的 `dataset@b227b896...`，禁止跟随分支头、Tag 漂移或下载最新版本。
3. **许可证证据完整性**：保存并校验数据集和 HowToCook 核验快照的 `LICENSE` 内容及 SHA-256，用于证明接入的仍是已核验固定版本；对当前固定提交而言这是防止输入漂移的完整性检查，不是新的许可证审批。只有切换到不同提交或证据内容发生变化时才重新评估。
4. **输入白名单**：导入器拒绝允许范围之外的路径；详情输入在 `recipes.json` 与 `recipes/*.json` 中二选一。
5. **离线与可复现**：在构建前离线导入，输出由固定输入和固定导入器确定；运行时不请求上游 API、GitHub、LFS 或图片服务。
6. **结构校验**：为索引和详情定义严格 schema，拒绝未知危险字段、绝对 URL、图片字段、HTML/脚本、重复 ID、缺失来源和超限文本。
7. **溯源完整性**：每条入库记录都必须能关联 `markdown_path`、`json_path`、源记录摘要和数据集固定提交；缺失项隔离而非静默补齐。
8. **内容与健康审核**：检查过敏原、禁忌、单位、份量、极端热量、错误食材和医疗化表述；第三方数据不能绕过本项目 AI 输出和健康提示的安全规则。
9. **最小化处理**：只保留产品实际需要的文本字段；移除所有图片信息、远程地址、无用元数据和可能含个人信息的自由文本。
10. **归属展示**：仓库 NOTICE、机器可读 provenance 和小程序内“开源与数据来源”同时完成，并以固定提交链接展示。
11. **测试门禁**：覆盖确定性导入、重复导入幂等、恶意字段拒绝、条目去重、来源映射、许可证快照和无网络运行测试。
12. **发布复核**：安全扫描确认没有 BUSL 代码、图片、热链和临时下载文件；人工审核差异后才允许合并与发布。

任一门禁失败时，默认行为是“不导入”。不得退回在线抓取、运行时 API 或无来源的静态副本作为替代。

## 7. 更新与删除策略

- 上游有新提交时必须视为一次新的数据版本，不得直接覆盖旧快照。
- 更新到不同上游提交前重新核对许可证、文件范围、数据 schema 和 provenance；当前已固定并核验的 `b227b896...` JSON 不需要重复等待许可证批准。使用新增版本号保留审计链。
- 菜谱稳定 ID 与用户个人调整必须分离。基础数据升级不得覆盖用户保存的个人餐食方案、采购状态或历史餐单。
- 若发现许可、来源或内容问题，应能按 provenance 精确撤下相关基础条目，而不是删除用户私人数据或清空整个数据库。
- 回滚只切换基础数据版本；用户数据继续按既有 schema 增量迁移和隔离保存。
